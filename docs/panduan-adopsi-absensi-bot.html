1. Ringkasan Adopsi

Adopsi di tempat lain berarti menjalankan salinan aplikasi yang sama, menghubungkannya ke basis data absensi setempat, dan mendaftarkan bot Telegram baru untuk lokasi tersebut.

Aplikasi terdiri atas tiga komponen utama. Pemahaman atas ketiga komponen ini menentukan lingkup pekerjaan saat berpindah server.

Telegram
Pengguna, grup, dan dept head
 →
Bot Absensi
Node.js, pembacaan data, format laporan
 →
SQL Server
Basis data ZKTeco lokal
Komponen Yang dipindahkan Catatan
Aplikasi Node.js Berkas sumber, dependensi, konfigurasi proses Tidak menyimpan basis data lokal
Konfigurasi .env baru Disusun ulang untuk server, basis data, dan bot baru
Bot Telegram Token dan daftar chat Satu token hanya untuk satu proses polling
Basis data Tidak dipindahkan oleh bot Menjadi tanggung jawab tim basis data setempat
Prinsip utama

Jangan menyalin berkas .env lama. Berkas tersebut memuat kredensial, token, dan daftar chat milik instalasi sebelumnya. Selalu buat konfigurasi baru untuk lokasi baru.

2. Prasyarat Server Baru

Siapkan server tujuan sebelum menyalin aplikasi. Kebutuhan minimum berikut harus terpenuhi agar layanan dapat berjalan dan dirawat.

2.1 Perangkat lunak

  • Node.js versi 18 atau lebih baru, beserta npm.
  • PM2 untuk pengelolaan proses dan pengaturan otomatis saat server menyala.
  • Akses ke SQL Server ZKTeco setempat, umumnya melalui port 1433.
  • Akses keluar HTTPS ke api.telegram.org.
  • Bot Telegram baru yang didaftarkan melalui @BotFather.

2.2 Jaringan dan akun

Kebutuhan Tujuan Keterangan
Koneksi SQL Server Membaca data absensi Gunakan akun khusus dengan izin baca saja
Koneksi Telegram Polling perintah dan pengiriman laporan HTTPS keluar, bukan koneksi masuk
Token bot baru Identitas bot pada lokasi baru Jangan memakai token bot instalasi lama
Zona waktu server Penentuan tanggal dan bulan berjalan Atur melalui variabel TZ
Satu token, satu proses

Telegram hanya mengizinkan satu proses polling untuk setiap token bot. Jika token yang sama dipakai di dua server, kedua proses akan saling menghentikan permintaan dan muncul kesalahan 409. Buat bot baru untuk lokasi baru.

2.3 Struktur direktori yang disarankan

/opt/absensi-bot/          # aplikasi
/opt/absensi-bot/.env       # konfigurasi lokal, izin 600
/opt/absensi-bot/logs/      # log aplikasi
/opt/absensi-bot/.bot.pid   # kunci proses, dibuat otomatis

3. Menyalin Aplikasi

Salin berkas proyek dari instalasi lama atau dari repositori sumber. Jangan menyalin direktori node_modules, berkas log, kunci proses, dan konfigurasi lama.

3.1 Perintah penyalinan

mkdir -p /opt/absensi-bot
rsync -av --exclude node_modules \
  --exclude logs \
  --exclude .env \
  --exclude .bot.pid \
  ./ /opt/absensi-bot/

cd /opt/absensi-bot
npm ci

Gunakan npm ci jika berkas package-lock.json tersedia. Jika tidak tersedia, gunakan npm install. Keduanya memasang dependensi yang dibutuhkan, terutama paket mssql.

3.2 Berkas yang wajib ikut

Berkas atau direktori Fungsi
src/ Logika bot, koneksi basis data, laporan, dan format tanggal
test/ Pengujian tanpa koneksi basis data dan tanpa token Telegram
package.json Daftar dependensi dan perintah menjalankan aplikasi
package-lock.json Kunci versi dependensi agar instalasi konsisten
ecosystem.config.cjs Konfigurasi proses PM2
.env.example Acuan penyusunan konfigurasi baru
README.md, PANDUAN.md Dokumentasi teknis dan panduan pengguna
Hak akses berkas

Setelah konfigurasi dibuat, batasi akses dengan chmod 600 .env. Pemilik direktori sebaiknya akun layanan khusus, bukan pengguna umum.

4. Menyusun Konfigurasi .env

Semua pengaturan runtime berada di .env. Mulai dari contoh resmi, lalu isi nilai untuk lokasi baru. 

cd /opt/absensi-bot
cp .env.example .env
chmod 600 .env
nano .env

4.1 Konfigurasi minimum

# Basis data ZKTeco lokal
DB_HOST=10.0.0.10
DB_PORT=1433
DB_USER=attendance_bot
DB_PASSWORD=isi-password-kuat
DB_NAME=attendance_db

# Telegram
TG_TOKEN=isi-token-bot-baru
ALLOWED_CHATS=
DEPT_HEADS=

# Aturan laporan
EXCLUDE_DEPARTMENTS=
LATE_TOLERANCE_MIN=10
CHECKOUT_NEAR_MIN=60
LEMBUR_MIN_MEN=240
SCHEDULE_FROM_DB=true
BASELINE_DAYS=30
ZK_WEEKDAY_MONDAY_IS_1=true

# Zona waktu
TZ=Asia/Jakarta

4.2 Penjelasan variabel utama

Variabel Fungsi
DB_HOST Alamat SQL Server tujuan. Ganti nilai bawaan yang masih mengarah ke server lama.
DB_PORT Port SQL Server. Umumnya 1433.
DB_USER, DB_PASSWORD Akun basis data dengan izin baca. Jangan gunakan akun administrator.
DB_NAME Nama basis data absensi ZKTeco.
TG_TOKEN Token bot Telegram baru dari @BotFather.
ALLOWED_CHATS Daftar chat ID dengan akses penuh, dipisahkan koma.
DEPT_HEADS Pemetaan chatId=nama departemen untuk akses terbatas.
EXCLUDE_DEPARTMENTS Departemen yang tidak dihitung, misalnya departemen karyawan resign.
LATE_TOLERANCE_MIN Toleransi keterlambatan dalam menit.
SCHEDULE_FROM_DB true memakai jadwal ZKTeco; false selalu memakai median historis.
ZK_WEEKDAY_MONDAY_IS_1 Pemetaan hari ZKTeco. Sesuaikan dengan pola data setempat.
TZ Zona waktu untuk menentukan hari ini dan bulan berjalan.

4.3 Pengaturan akses pengguna

Setelah bot berjalan, kirim /id dari chat yang akan diizinkan. Salin chat ID ke salah satu variabel berikut, lalu mulai ulang bot. 

# Akses penuh ke semua departemen
ALLOWED_CHATS=100000001,-1001234567890

# Akses terbatas per departemen
DEPT_HEADS=100000003=IT,100000004=HR
Jangan biarkan akses terbuka

Jika ALLOWED_CHATS dan DEPT_HEADS sama-sama kosong, siapa pun yang menemukan bot dapat membaca data absensi. Isi salah satu sebelum bot dipakai di lingkungan produksi.

Catatan: chat yang terdaftar di DEPT_HEADS selalu dibatasi ke departemennya, walaupun juga tercantum di ALLOWED_CHATS.

5. Memeriksa Kompatibilitas Basis Data

Versi aplikasi ini ditujukan untuk SQL Server dengan skema ZKTeco. Periksa kecocokan tabel dan kolom sebelum menghubungkan bot ke basis data baru.

5.1 Tabel dan kolom yang digunakan

Tabel Kolom Kegunaan
USERINFO USERID, BADGENUMBER, NAME, DEFAULTDEPTID Daftar karyawan dan departemen
DEPARTMENTS DEPTID, DEPTNAME Nama departemen
CHECKINOUT USERID, CHECKTIME, CHECKTYPE Riwayat punch masuk dan pulang
USER_OF_RUN USERID, NUM_OF_RUN_ID, STARTDATE, ENDDATE Penugasan jadwal karyawan
NUM_RUN NUM_RUNID, STARTDATE, CYLE, UNITS Siklus jadwal
NUM_RUN_DEIL NUM_RUNID, SDAYS, STARTTIME, ENDTIME Detail hari dan jam shift

5.2 Hal yang perlu diperiksa

  • Nama skema. Query memakai nama tabel tanpa awalan skema, sehingga mengikuti default schema akun basis data. Jika tabel berada di skema tertentu, sesuaikan query atau default schema akun.
  • Versi ZKTeco. Beberapa versi memiliki nama kolom atau struktur jadwal yang berbeda. Bandingkan dengan tabel di atas.
  • Isi CHECKTYPE. Nilai I dan O dipakai untuk membedakan punch masuk dan pulang. Jika kolom ini kosong, bot memakai urutan waktu punch.
  • Zona waktu data. Jam dibaca sebagai string dari SQL Server agar tidak bergeser oleh konversi JavaScript. Pastikan zona waktu server dan data konsisten.
  • Mesin basis data. Jika tujuan bukan SQL Server, driver dan seluruh query perlu diganti. Aplikasi memakai paket mssql.

5.3 Akun basis data baca saja

Buat akun khusus untuk bot. Contoh perintah berikut dapat disesuaikan dengan kebijakan keamanan setempat. 

CREATE LOGIN attendance_bot WITH PASSWORD = 'ganti-password-kuat';
USE attendance_db;
CREATE USER attendance_bot FOR LOGIN attendance_bot;
ALTER ROLE db_datareader ADD MEMBER attendance_bot;
Bot tidak menulis data

Seluruh operasi aplikasi bersifat baca. Jangan memberikan izin INSERT, UPDATE, atau DELETE kepada akun bot.

5.4 Jika struktur berbeda

Penyesuaian query dilakukan di src/schedule.js. Koneksi dan tipe parameter berada di src/db.js. Setelah perubahan, jalankan npm test dan uji perintah laporan pada data nyata.

6. Menyesuaikan Nilai Bawaan dan Dokumentasi

Aplikasi dapat berjalan tanpa perubahan kode selama .env diisi dengan benar. Namun, beberapa nilai bawaan masih merujuk pada instalasi asal dan sebaiknya diperbarui agar tidak menimbulkan kesalahan operasional.

Lokasi Penyesuaian yang disarankan
src/config.js Ganti nilai bawaan DB_HOST yang masih mengarah ke server lama.
ecosystem.config.cjs Ubah nama aplikasi jika satu server menjalankan lebih dari satu instalasi.
README.md Perbarui alamat server, username bot, dan contoh perintah grup.
PANDUAN.md Ganti nama bot contoh dan lokasi direktori agar sesuai instalasi baru.

6.1 Dua instalasi pada satu server

Setiap instalasi harus memiliki direktori, token, dan nama proses PM2 yang berbeda. Berkas .bot.pid juga terpisah karena berada di dalam direktori masing-masing. 

apps: [
  {
    name: 'absensi-bot-site2',
    script: 'src/bot.js',
    cwd: __dirname,
    instances: 1,
    exec_mode: 'fork',
    autorestart: true,
    max_memory_restart: '300M',
    time: true,
    env: { NODE_ENV: 'production' },
  },
]
Jangan menyalin kunci proses

Berkas .bot.pid hanya berlaku pada server dan proses yang sedang aktif. Hapus berkas tersebut dari hasil salinan jika masih ada.

7. Menjalankan Layanan

Jalankan pengujian terlebih dahulu. Pengujian tidak memerlukan koneksi basis data maupun token Telegram. 

cd /opt/absensi-bot
npm test

Setelah pengujian lulus, jalankan aplikasi melalui PM2 agar proses tetap hidup dan otomatis dimulai kembali bila berhenti. 

pm2 start ecosystem.config.cjs
pm2 save
pm2 startup
pm2 logs absensi-bot

Perintah pm2 startup menampilkan instruksi tambahan. Jalankan perintah yang ditampilkan agar proses terdaftar pada layanan sistem.

7.1 Perintah operasional

Perintah Fungsi
pm2 status Melihat status seluruh proses
pm2 logs absensi-bot Melihat log aplikasi secara langsung
pm2 restart absensi-bot Memuat ulang aplikasi dan konfigurasi
pm2 stop absensi-bot Menghentikan proses tanpa menghapus konfigurasi
pm2 delete absensi-bot Menghapus proses dari daftar PM2

7.2 Lokasi log

Aplikasi menulis log ke logs/bot.log. PM2 juga menyimpan log proses tersendiri. Periksa keduanya saat terjadi kegagalan koneksi atau kesalahan token.

7.3 Menjalankan tanpa PM2

Untuk pengujian singkat, jalankan npm start dari direktori aplikasi. Pastikan tidak ada proses lain yang memakai token yang sama.

8. Verifikasi Pascainstalasi

Lakukan pemeriksaan berikut sebelum bot diserahkan kepada pengguna. Urutan ini memastikan koneksi, akses, dan perhitungan laporan bekerja dengan benar.

  1. Kirim /start ke bot baru dari akun administrator.
  2. Kirim /id, lalu catat chat ID yang muncul.
  3. Isi ALLOWED_CHATS atau DEPT_HEADS, lalu mulai ulang bot.
  4. Kirim /today dan bandingkan angka dengan data pada basis data.
  5. Uji /terlambat dan /hadir untuk satu tanggal yang diketahui.
  6. Uji /bulan untuk memastikan rekap bulanan dan nama departemen benar.
  7. Periksa pola shift. Jika hari bergeser, sesuaikan ZK_WEEKDAY_MONDAY_IS_1.
  8. Uji akses dept head dan pastikan hanya data departemennya yang tampil.
  9. Kirim perintah dari grup untuk memastikan privacy mode sudah ditangani.

8.1 Indikator keberhasilan

Pemeriksaan Hasil yang diharapkan
Log aplikasi Tidak ada kesalahan koneksi basis data atau token
Perintah /today Ringkasan tampil dan sesuai data setempat
Akses chat Chat tidak terdaftar menerima pesan akses ditolak
Dept head Hanya melihat departemen yang ditetapkan
Proses PM2 Status online dan restart stabil

9. Keamanan dan Operasional

Data absensi bersifat sensitif. Terapkan pengendalian berikut pada setiap instalasi, bukan hanya pada instalasi pertama.

9.1 Daftar kendali keamanan

  • Berkas .env memiliki izin 600 dan tidak masuk repositori.
  • Akun basis data hanya memiliki izin baca.
  • Password basis data tidak memakai akun sa.
  • Port SQL Server tidak terbuka ke internet umum.
  • ALLOWED_CHATS atau DEPT_HEADS sudah diisi.
  • Token bot tidak dibagikan melalui dokumen, tangkapan layar, atau chat.
  • Satu token hanya dipakai satu proses polling.
  • Log dan berkas konfigurasi tidak dapat dibaca pengguna umum.

9.2 Rutinitas perawatan

Kegiatan Frekuensi Tujuan
Pemeriksaan status PM2 Mingguan Memastikan proses berjalan dan tidak restart berulang
Pemeriksaan log Mingguan Mendeteksi kesalahan koneksi atau token lebih awal
Rotasi log Sesuai kebijakan Mengendalikan penggunaan disk
Peninjauan akses chat Berkala Menghapus akses pengguna yang tidak lagi berwenang
Pembaruan dependensi Berkala Memperoleh perbaikan keamanan

9.3 Pencadangan

Aplikasi tidak memiliki basis data lokal, sehingga pencadangan utama mencakup berkas konfigurasi dan salinan kode. Pencadangan data absensi merupakan tanggung jawab pengelola SQL Server.

Simpan salinan konfigurasi dengan aman

Simpan .env pada penyimpanan rahasia yang terkendali. Jangan menaruh salinannya di repositori kode atau folder berbagi publik.

10. Penanganan Masalah Umum

Gejala Penyebab yang mungkin Tindakan
Bot tidak menjawab di grup Privacy mode Telegram masih aktif Alamatkan perintah ke bot atau ubah pengaturan melalui @BotFather
Pesan akses ditolak Chat ID belum terdaftar Kirim /id, tambahkan ID, lalu mulai ulang bot
Gagal mengambil data absensi Koneksi, kredensial, atau timeout basis data Periksa log dan variabel DB_*
Kesalahan token tidak valid Token salah atau sudah dicabut Ambil token baru dari @BotFather
Kesalahan 409 Dua proses memakai token yang sama Hentikan proses lama, jalankan satu instance saja
Terlambat tidak sesuai Toleransi, pemetaan hari, atau jadwal berbeda Periksa LATE_TOLERANCE_MIN, ZK_WEEKDAY_MONDAY_IS_1, dan data jadwal
Tanggal atau bulan bergeser Zona waktu tidak sesuai Sesuaikan TZ, lalu mulai ulang bot
Laporan terpotong Batas panjang pesan Telegram Persempit rentang tanggal atau gunakan nama karyawan

10.1 Lokasi pemeriksaan

  • logs/bot.log untuk log aplikasi.
  • pm2 logs absensi-bot untuk log proses dan keluaran standar.
  • .env untuk kredensial dan aturan laporan.
  • Tabel ZKTeco untuk membandingkan hasil laporan dengan data sumber.

Lampiran A. Contoh Konfigurasi Lengkap

Contoh berikut dapat disalin ke .env, lalu disesuaikan dengan lingkungan setempat. Nilai rahasia tidak boleh dimasukkan ke dokumen publik. 

# ---------------------------------------------------------
# Basis data ZKTeco (SQL Server)
# ---------------------------------------------------------
DB_HOST=10.0.0.10
DB_PORT=1433
DB_USER=attendance_bot
DB_PASSWORD=ganti-password-kuat
DB_NAME=attendance_db
DB_ENCRYPT=false
DB_TRUST_SERVER_CERTIFICATE=true
DB_CONNECTION_TIMEOUT_MS=15000
DB_REQUEST_TIMEOUT_MS=30000

# ---------------------------------------------------------
# Telegram
# ---------------------------------------------------------
TG_TOKEN=ganti-token-bot-baru
TG_NOTIFY_TOKEN=
TG_NOTIFY_CHAT=
TG_CHAT_NAMES=

# Kosong berarti semua chat boleh mengakses.
# Isi chat ID untuk membatasi akses.
ALLOWED_CHATS=

# Format: chatId=nama departemen, dipisahkan koma.
DEPT_HEADS=

# ---------------------------------------------------------
# Aturan laporan
# ---------------------------------------------------------
EXCLUDE_DEPARTMENTS=
LATE_TOLERANCE_MIN=10
CHECKOUT_NEAR_MIN=60
LEMBUR_MIN_MEN=240
SCHEDULE_FROM_DB=true
BASELINE_DAYS=30
ZK_WEEKDAY_MONDAY_IS_1=true

# ---------------------------------------------------------
# Zona waktu
# ---------------------------------------------------------
TZ=Asia/Jakarta
Nilai yang wajib diganti

DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, dan TG_TOKEN harus diisi dengan nilai dari lingkungan baru. Jangan memakai nilai contoh apa adanya.

Lampiran B. Daftar Periksa Go-Live

Gunakan daftar ini sebagai gerbang akhir sebelum bot diumumkan kepada pengguna.

B.1 Infrastruktur

  • Node.js 18 atau lebih baru terpasang.
  • Dependensi terpasang melalui npm ci.
  • Koneksi ke SQL Server tujuan berhasil.
  • Akses keluar ke api.telegram.org tersedia.
  • PM2 menjalankan proses dengan status online.
  • Proses terdaftar untuk mulai otomatis saat server menyala.

B.2 Konfigurasi

  • .env baru sudah dibuat dan memiliki izin 600.
  • Token bot baru sudah dipasang.
  • ALLOWED_CHATS atau DEPT_HEADS sudah diisi.
  • Departemen yang dikecualikan sudah ditetapkan.
  • TZ sesuai lokasi.
  • Pemetaan hari ZKTeco sudah diverifikasi.

B.3 Fungsional

  • /start, /help, dan /menu bekerja.
  • /id menampilkan chat ID yang benar.
  • /today sesuai data setempat.
  • /terlambat dan /hadir menampilkan data yang benar.
  • /bulan menghitung rekap dengan benar.
  • Akses dept head terbatas pada departemennya.
  • Perintah dari grup dapat diproses.

B.4 Keamanan

  • Akun basis data hanya memiliki izin baca.
  • Password bukan milik akun administrator.
  • Token dan password tidak tercantum dalam dokumentasi publik.
  • Akses chat ditinjau dan sesuai daftar pengguna berwenang.
  • Log tidak dapat dibaca pengguna umum.
Dokumen ini merupakan panduan teknis adopsi. Perubahan pada kode, skema basis data, atau kebijakan keamanan setempat harus tercermin dalam versi dokumen berikutnya.
